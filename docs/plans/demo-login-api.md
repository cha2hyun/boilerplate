# 작업 계획: 데모 로그인 응답 상태

## 문제와 완료 조건

현재 폼은 탭의 세션 ID를 즉시 기록한다. 데모 로그인도 HTTP 응답을 기다리도록 바꿔, 이메일이나 Microsoft 버튼에서 대기·실패·재시도·성공을 직접 확인할 수 있게 한다. 보호 화면의 원래 주소로 돌아가는 흐름과 API 모드의 연결 안내는 유지한다.

## 확인한 근거

- [로그인 명세](../pages/login.md), [탭 세션](../../src/features/demo-session/model/session.ts), [데모 HTTP 핸들러](../../src/app/mocks/handlers.ts)를 확인했다.
- 기존 개발 서버는 LAN HTTP에서 MSW의 Fetch/XHR fallback을 사용한다. HTTPS 또는 localhost의 Service Worker 경로도 같은 핸들러를 사용해야 한다.

## 변경 경계

- 로그인 폼은 요청 중 표시, 오류·초점, 재시도와 이탈 시 취소를 소유한다. 데모 응답 선택은 현재 폼 안에만 둔다.
- 데모 세션 feature는 같은 출처의 고정 로그인 경로와 요청/응답 스키마를 소유한다. MSW는 자격 증명 확인과 시뮬레이션 지연을 수행한다. 검증된 성공 응답에서만 기존 탭 세션을 연다.
- 업무 API 주소, 워크스페이스 저장 형식, Microsoft 연동과 운영 인증은 이번 작업의 변경 범위 밖이다.

## 실행과 검증

1. 두 가지 로그인 요청과 성공·입력 불일치·서비스 실패의 상태 및 응답 형식을 검증한다.
2. 요청 중 중복 제출 방지, 오류 이후 재시도, 응답 전 이탈, 세션 확정 시점을 폼과 라우트에서 확인한다.
3. 로컬 정적 검사와 필요한 단위·브라우저 검사만 실행한다. 요청에 따라 GitHub Actions 상태는 조회하지 않는다.

## 완료 기록

- 로그인 폼에 한 번만 적용되는 응답 선택을 추가했다. 느린 응답 중 다른 방식으로 제출해도 요청은 하나이고, 서버 오류 뒤에는 입력을 보존해 같은 버튼으로 다시 시도할 수 있다.
- localhost Chromium의 Service Worker에서 200·400·401·503 응답을 확인했다. PC·태블릿·모바일의 로그인과 원래 주소 복귀, 서버 오류 재시도는 [브라우저 회귀 검사](../../e2e/workspace-users.spec.ts)에 반영했다.
- LAN HTTP의 모바일 WebKit에서도 느린 로그인과 실패·재시도가 동작했다. 대시보드로 이동하거나 문서를 떠나면 지연된 성공 응답으로 로그인되지 않았다.
- `pnpm check`, 로그인 API·세션·HTTP 클라이언트 단위 검사 42건, 폼 단위 검사 6건이 통과했다. 브라우저에서는 세 화면 구간의 공통 시나리오 9건과 서버 오류 후 재시도 1건이 통과했다.
