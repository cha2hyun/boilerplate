# 작업 계획: 데모 저장 검증과 새 도메인 포크

## 문제와 완료 조건

LAN HTTP에서 프로젝트·주문·고객을 만들고 새로고침해도 레코드가 남아야 한다. 두 탭이 같은 주문을 수정할 때 다른 탭의 확정된 변경을 덮어쓰지 않아야 한다. 포크한 팀은 주문·고객 샘플을 제거하고 새 도메인의 화면·API·검사를 연결할 수 있어야 한다.

## 확인한 근거

일반 LAN 브라우저에서 세 생성 경로의 UUID 생성 실패를 재현했다. 주문 상태를 변경한 뒤 오래된 폼으로 도시만 수정하면 상태가 되돌아갔다. 기존 포크 예시는 주문을 남기는 경로였다.

## 변경 경계

데모 생성 ID, 주문 편집 폼·목업·HTTP 갱신 계약, 포크 문서를 수정한다. 저장된 데모 레코드와 충돌 시 작성 중이던 입력을 보존한다. 포크 예시는 별도 복사본에서 검증한다.

## 실행과 검증

1. LAN에서 세 도메인의 생성·재조회와 기존 ID 충돌 처리를 확인한다.
2. 주문 변경이 겹친 두 탭을 재현하고 저장 결과와 편집 초안을 확인한다.
3. 원본 프로젝트와 별도의 포크 실습 결과를 구분해 기록한다. 원본에서는 정적 검사와 관련 회귀 검사를 실행한다.

## 완료 기록

- 일반 LAN HTTP에서 Chromium과 모바일 크기 WebKit으로 세 도메인마다 두 건을 생성하고 고유 ID와 새로고침 복원을 확인했다.
- 주문 데모와 HTTP·캐시·폼의 집중 단위 검사 86건이 통과했다. 느린 탭의 도시와 먼저 저장한 배송 상태가 함께 보존되고, 같은 필드를 서로 바꾸면 운영자가 저장값 또는 내 값을 선택할 때까지 저장이 잠긴다. 같은 버전의 동시 PATCH는 한 건만 확정됐고, 거절된 요청은 이력에 쓰이지 않았다. 잠금 저장소 접근 거부 시에는 탭의 변경이 기존 공유 저장소를 덮지 않았다.
- 원본에서 `pnpm check`와 빌드, 프로덕션 미리보기의 프로젝트·주문·고객 및 동시 편집 E2E 5건이 통과했다.
- 원본 기반 임시 클론에서 설비 점검 앱으로 교체했다. 정적 검사·빌드·초기 번들 예산, 새 업무와 공통 화면을 대상으로 한 브라우저 검사 13건을 확인했다. 실습 코드는 이 저장소에 포함하지 않는다. [포크 가이드](../examples/minimal-admin.md)
- 실제 외부 서버는 주문 버전을 제공하고 버전 비교와 쓰기를 원자적으로 구현해야 한다. GitHub Actions 상태는 사용자 요청에 따라 조회하지 않았다.
