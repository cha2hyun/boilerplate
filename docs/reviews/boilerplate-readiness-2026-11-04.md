## 확인하고 수정한 결함

1. **불확실한 쓰기 결과:** POST 저장 직후 연결이 끊기거나 2xx 응답만 잘못된 경우 일반 재시도를 권했다. [HTTP 경계](../../src/shared/api/client.ts)와 [번역 경계](../../src/shared/lib/i18n/use-error-message.ts)가 저장 가능성과 재확인 안내를 보존한다. [프로젝트 mutation](../../src/entities/project/api/queries.ts)은 이전 조회를 취소한 뒤 무효화/재조회하고 성공을 추측하지 않는다. 서버 idempotency는 별도 통합 계약이다.
2. **서로 다른 timezone의 수정일 정렬:** [프로젝트 표](../../src/widgets/project-table/ui/project-table.tsx)는 문자열 대신 timestamp로 정렬한다. `10:00+09:00`과 `09:00Z`의 실제 선후관계를 양방향 정렬 테스트로 확인했다.
3. **최근 매출 기간:** [응답 스키마](../../src/entities/analytics/model/schema.ts)가 날짜 중복을 거부하고 순서를 정규화한다. [기간 선택](../../src/entities/analytics/model/revenue.ts)은 마지막 제공일부터 실제 N일을 계산한다. 날짜 누락을 오래된 항목이나 가짜 0으로 채우지 않는다.
4. **목록 실패 안내:** [주문](../../src/pages/orders/ui/orders-page.tsx)과 [고객](../../src/pages/customers/ui/customers-page.tsx)의 최초 조회 실패를 0건으로 알리던 분기를 고쳤다. 오류 영역만 알림을 담당하고 footer의 중복 live 안내를 피한다.
5. **좁은 고객 상세의 원화 금액:** 320px에서 `₩2,050,255`가 카드 밖으로 나가는 것을 재현했다. 상세 content 폭에 따른 container query로 320px에서는 한 열, 390px에서는 두 열을 사용한다. 수정 후 카드 scroll/client 너비가 각각 269/269와 163/163이었다.
6. **차트 접근 가능한 이름:** wrapper에만 있던 이름을 실제 Recharts `application`으로 옮겼다. 분석 화면의 두 차트 이름을 브라우저 접근성 트리에서 확인했다. 공통 shadcn chart primitive는 수정하지 않았다.
7. **CI 테스트 범주 누락:** [정적 검사기](../../scripts/check-e2e-categories.mjs)가 발견된 E2E 파일과 core/samples 목록을 대조한다. 누락·중복·없는 경로를 실패 처리하며 편의 명령은 중복 실행 범주로 세지 않는다.

통화 메뉴의 설명/날짜 삭제와 Banknote 아이콘 변경은 사용자 요청에 따른 UI 정리이며 품질 결함으로 감점하지 않았다. 환율 날짜는 응답 검증/캐시에 남는다.

낮은 우선순위의 **미확인 후보**는 공백 없는 80자 프로젝트명을 삭제 확인창에 넣었을 때의 줄바꿈이다. 코드상 wrapping 규칙이 없지만 이번 브라우저 검증에서 재현하지 않았으므로 확정 결함 목록에 넣지 않는다.

새 제품 도입 절차는 [별도 체크리스트](../new-project.md)에 두었다. 실제 서버·인증·배포의 완료 조건은 [운영 전환](../production-readiness.md)을 따른다. 이를 보일러플레이트에 없는 제품 기능이라는 이유만으로 감점하지 않았다.

## 검증 범위

- 로컬은 `pnpm check` 정적 검사와 결함에 직접 관련된 8개 파일의 36개 단위 테스트, 새 범주 검사기 6개 회귀 테스트만 실행했다. 전체 테스트/빌드를 로컬에서 반복하지 않는다.
- 현재 dev 서버에서 통화 메뉴를 desktop/tablet/mobile로 확인하고, 실제 데이터의 고객 상세 320/390px와 차트 접근성 이름을 확인했다. 이것을 production E2E 결과로 간주하지 않는다.
- 기존 E2E 흐름에 최초 오류→재시도 회복, 320px KRW 카드 경계, 실제 차트 이름을 추가했다. 전체 단위/가드레일과 동일 production bundle의 core/samples·3개 화면 크기는 해당 PR 및 최종 main SHA의 Actions로 확인한다. 최종 실행 링크는 PR/작업 완료 기록을 기준으로 삼는다.
