# URL 조회 상태

차트 기간, 목록 검색·필터·정렬·페이지는 TanStack Router의 search state가 소유합니다. 새로고침, 직접 링크, 브라우저 뒤로/앞으로 이동에서 같은 조회 조건을 복원합니다. 이 상태를 useState·Zustand·localStorage에 복제하지 않습니다.

## 화면별 계약

| 경로         | 저장하는 값                                                      |
| ------------ | ---------------------------------------------------------------- |
| `/`          | 매출 `period`, 프로젝트 요약 표의 `sort`, `order`, 상세 `detail` |
| `/projects`  | `q`, `status`, `sort`, `order`, `page`, `pageSize`, `detail`     |
| `/analytics` | 지표·차트·유입 표가 공유하는 `period`                            |
| `/orders`    | `q`, `status`, `sort`, `page`, `pageSize`, `detail`              |
| `/customers` | `q`, `status`, `sort`, `page`, `pageSize`, `detail`              |
| `/users`     | `q`, `status`, 구성원 상세 `id`                                  |
| `/inbox`     | `q`, `view`                                                      |

페이지 번호는 URL에서 1부터 시작합니다. Orders/Customers는 6/12/24, Projects는 해당 모델의 선택 가능한 페이지 크기를 URL에 저장합니다. 필터·정렬·페이지 크기를 바꾸면 페이지를 1로 되돌립니다. 차트 기간은 기존 화면의 7/14/30일을 사용합니다.

홈의 프로젝트 요약 표와 Projects·Orders·Customers의 상세 패널은 URL `detail` ID가 소유합니다. 프로젝트는 필터·페이지 적용 전 전체 프로젝트 Query에서 ID를 찾습니다. 상세 링크·새로고침·뒤로/앞으로에서 같은 레코드를 복원하며 조회 조건은 유지합니다. 존재하지 않거나 삭제된 ID는 조회 성공 후 설명과 목록 복귀로 처리하고 조용히 닫지 않습니다. 행 선택, 생성/편집/삭제 대화상자·모바일 요약 펼침은 임시 UI 상태입니다. Projects·Orders·Customers의 열 표시·순서·너비·고정·행 간격은 아래 표 보기 환경 설정으로 저장합니다. Inbox의 읽음/보관 변경은 기존 메모리 샘플이며 URL에 저장하지 않습니다. 언어·통화·테마는 기존 환경 설정 계약을 유지합니다. 컴포넌트·디자인 기준 페이지의 체험용 컨트롤은 목록 조회 조건이 아닙니다.

[Users](pages/users.md)는 목록을 `q`·`status`로 거르고, 필터 밖의 구성원도 URL의 `id`로 상세를 조회합니다. 상세를 닫으면 `id`만 비우고 목록 조건을 유지합니다.

## 표 보기 환경 설정

[공통 표 보기 기능](../src/features/table-view/index.ts)은 Projects·Orders·Customers의 열 표시·순서·너비·왼쪽/오른쪽 고정·행 간격을 표 ID별 Zustand 상태로 관리합니다. 이 값은 어떤 행을 조회할지 바꾸지 않으므로 URL·Query 키·API 요청에 넣지 않습니다. 행 데이터나 프로젝트/주문/고객 식별자도 보기 설정에 저장하지 않습니다.

- `blueprint-table-views`의 버전 1 형식을 Zod로 검증한 뒤 복원합니다. 손상된 표 설정은 그 표의 기본값으로 복구하고 정상적인 다른 표 설정은 유지합니다. 지원하지 않는 저장 버전은 기본값으로 돌아갑니다.
- 현재 코드의 열 정의가 허용 ID·기본 너비·최소/최대 너비·숨김 가능 여부·잠긴 열을 소유합니다. 저장된 알 수 없는 ID와 중복을 제거하고 새 열을 포함합니다. 표시 이름은 현재 언어에서 계산하며 저장된 문자열로 대체하지 않습니다.
- 보기 변경은 URL이나 브라우저 방문 기록을 바꾸지 않습니다. 새로고침하면 같은 브라우저의 최근 보기 설정을 복원하고, 뒤로/앞으로 이동은 URL 조회 조건만 복원합니다. 목록 필터 초기화는 보기 설정을 유지하고 **기본값 복원**은 해당 표의 보기 설정만 되돌립니다.
- 좁은 화면에서 고정 열이 스크롤할 본문 공간을 가리면 고정을 일시 중단합니다. 저장한 너비·순서·고정 선택은 유지하며 화면이 넓어지면 다시 적용합니다. Overview의 최근 프로젝트 요약은 전체 Projects 표의 보기 설정을 적용하지 않습니다.
- 브라우저 저장이 실패하면 현재 탭의 메모리 설정으로 계속 사용합니다. 이 경우 새로고침 후 유지되지 않을 수 있습니다. 실제 사용자 계정별 서버 저장·다른 기기 동기화는 구현하지 않습니다.

숫자 너비·고정 위치의 UI 경계는 [ADR 007](adr/007-table-view-geometry.md), 표별 기본값과 행동은 [Projects](pages/projects.md)·[Orders](pages/orders.md)·[Customers](pages/customers.md) 기획을 따릅니다.

## 검증과 소유 위치

- 화면의 `model/search.ts`에서 Zod 스키마·출력 타입·기본값을 정의합니다. 여러 화면이 쓰는 프로젝트 표·매출 기간 계약은 해당 위젯 모델이 소유합니다. 기존 `index.ts` 공개 API는 유지하고, 위 표의 조회 페이지와 두 위젯은 같은 계약을 루트 `search.ts`에서도 named re-export합니다. 스키마·기본값을 복제하지 않습니다. 허용 목록과 런타임 UI 의존 차단은 [아키텍처](architecture.md)와 [ADR 006](adr/006-search-public-entrypoints.md)을 따릅니다.
- `app/routes`가 Zod 4 스키마를 `validateSearch`에 직접 전달합니다. 추가 어댑터는 필요하지 않습니다. 검증된 search와 탐색 콜백을 페이지·위젯에 props로 전달합니다.
- 라우트는 Page 컴포넌트를 `index.ts`에서, 조회 계약을 `search.ts`에서 각각 가져옵니다. Router의 자동 코드 분리와 intent preload는 유지하며 수동 lazy wrapper, 추가 Suspense, 조회 지연을 넣지 않습니다. Overview 모델이 프로젝트 표와 매출 기간을 조합할 때도 위젯의 `search.ts`를 사용하여 UI로 이어지는 정적 연결을 만들지 않습니다.
- 기본값은 스키마와 탐색에서 공유하고 `stripSearchParams`로 기본값인 필드를 URL에서 생략합니다. 앱의 `search.strict`로 스키마에 없는 필드가 탐색 상태에 전파되지 않게 합니다.
- 필드마다 `.default`와 `.catch`로 누락·잘못된 값을 복구합니다. 한 필드 오류 때문에 나머지 정상 조건을 지우거나 페이지 오류 화면을 띄우지 않습니다.
- 상세 ID는 최대 200자의 opaque 문자열이며 숫자로 파싱된 ID는 문자열로 복원합니다. 형식이 잘못되면 상세만 기본값으로 복구하고 정상 조회 조건을 보존합니다. 비밀과 개인정보 원문을 ID로 사용하지 않습니다.
- 공통 검색어는 최대 200자, 페이지는 1~100,000의 정수만 허용합니다. 배열·객체·boolean을 문자열/숫자로 무조건 강제 변환하지 않습니다. 입력창에도 같은 최대 길이를 적용합니다.
- Router는 URL의 JSON 값을 먼저 파싱합니다. 숫자로 파싱되는 기간은 허용된 기간으로만 변환하고, 숫자 검색어는 문자열로 복원합니다. URL은 Router로 직렬화하며 `URLSearchParams`/`window.history`를 직접 수정하지 않습니다.
- 조회 성공 후 실제 마지막 페이지보다 큰 번호는 마지막 페이지로 `replace`합니다. 데이터가 아직 없거나 조회 중·실패인 시점에 페이지 번호를 초기화하지 않습니다.

## 탐색과 Query

선택 필터·정렬·탭·페이지 이동·상세 열기/닫기·초기화는 history push를 사용합니다. 텍스트 입력은 현재 항목을 replace하여 글자마다 방문 기록을 만들지 않습니다. 따라서 뒤로 가기는 선택 단계나 이전 페이지로 돌아가며 글자 단위 실행 취소가 아닙니다. 조회 조건 변경은 `resetScroll: false`로 화면 위치를 유지합니다.

여러 조건을 한 번에 바꿀 때 한 search updater로 원자적으로 갱신하고, 다른 조건은 보존합니다. URL을 읽은 뒤 별도 effect로 로컬 필터와 양방향 동기화하지 않습니다. Query 키에는 실제 요청을 바꾸는 검증된 조건만 포함합니다. Analytics는 기간별 Query 키를 사용합니다. Orders는 검증한 검색·상태·정렬·페이지·페이지 크기를 목록 Query 키와 HTTP 요청에 넣으며 상세 ID와 전체 요약은 별도 Query입니다. 클라이언트에서 거르는 Projects/Customers/Users 목록은 원본 목록 캐시를 재사용합니다. URL에 비밀이나 인증 토큰을 넣지 않습니다.

## 검증

- 스키마 테스트: 기본값, 허용 값, JSON 형태가 다른 입력, 범위 밖 페이지, 잘못된 필드와 정상 필드의 공존을 검사합니다.
- 조회 공개 진입점 검사는 정확한 공개 경로·named re-export·타입 전용 연결을 확인하고, 간접 barrel/동적 import/확장자를 생략한 TSX를 통한 UI 유입을 거부합니다. 기존 URL 스키마 값과 탐색 props는 변경하지 않습니다.
- 기존 E2E 범주에서 컨트롤→URL, 새로고침, 뒤로/앞으로, 잘못된 직접 링크, 데이터 조회 뒤 페이지 보정을 검증합니다.
- 공통 Router 직렬화 테스트는 한국어·예약 문자·숫자 검색어를 확인합니다. 전체 브라우저 검사는 Actions의 기존 production 번들과 2-job/2-worker 구성을 사용합니다.

기반 API는 [TanStack Router 검색 파라미터 검증](https://tanstack.com/router/latest/docs/how-to/validate-search-params)과 [탐색 옵션](https://tanstack.com/router/latest/docs/api/router/NavigateOptionsType)을 따릅니다.

Orders의 검색·정렬·페이지 보정은 API 어댑터 계약이 소유하며 페이지는 검증된 응답의 행·전체 수·페이지를 표시합니다. 성공 응답의 보정된 페이지는 URL에 replace하고 로딩/실패에서는 복원한 URL을 초기화하지 않습니다. 상세는 현재 목록에 포함되지 않은 ID도 별도로 조회합니다. Customers의 클라이언트 조회 계산은 `model/selectors.ts`가 소유하고, 응답과 실제 조회 조건만 memo 의존성에 넣어 상세 ID·폼 상태 변경 때 재정렬하지 않습니다. 데모에서는 MSW가 Orders의 서버 계약을 모방하며 실제 운영 서버나 가상화가 구현된 것은 아닙니다.
